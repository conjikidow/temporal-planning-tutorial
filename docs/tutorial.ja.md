# チュートリアル

[English](tutorial.md) | **日本語**

小さな時間モデルを読んで完成させ，プランナーから返ってきた実行できないプランをもとに，モデルの不足を補います。

必要なツールと，それらを入れるコマンドは，README の [必要なもの](../README.ja.md#必要なもの) にまとめてあります。
README を読み進める場合は [シナリオ](../README.ja.md#シナリオ) の手前で止めてください。
その節から下では模範解答を説明するため，ステップ2とステップ3の答えが分かってしまいます。

## 開始地点

リポジトリをクローンします。

```bash
git clone https://github.com/conjikidow/temporal-planning-tutorial.git
cd temporal-planning-tutorial
uv sync
```

`main` には模範解答が入っているため，そこから始めると答えを見てしまいます。
代わりに，自分のブランチを切って最初のチェックポイントから始めます。

```bash
git switch -c tutorial-work step-0
```

4つのステップはすべて同じブランチで，[`models/pddl/`](../models/pddl/) 以下のファイルを直接編集して進めます。
各ステップは，そのステップの開始状態をタグから取り込むところから始まり，行き詰まったときのやり直しにも同じタグを使います。
[チェックポイント](#チェックポイント) を参照してください。

## ステップ0: モデルを読んで実行する

次の順で2つのファイルを読みます。

- [`models/pddl/domain.pddl`](../models/pddl/domain.pddl) は **ドメイン** です。
  どのような種類のオブジェクトが登場しうるか，それらについてどのような事実が成り立ちうるか，そして衛星がどのようなアクションを実行できるかを書きます。
  ここに書くのは個々のミッションの中身ではなく衛星そのものの仕様なので，いつ実行するミッションでも内容は同じです。
- [`models/pddl/problem.pddl`](../models/pddl/problem.pddl) は **問題** です。
  今回のミッションにどのオブジェクトが実在し，開始時にどの事実が真であり，終了時にどの事実が真になっていなければならないかを書きます。
  ドメインで記述した衛星に対する，1回分の具体的な要求です。
  `(:objects)` には2つのターゲットが並んでいるのに対し，ゴールが名指しするのは1つだけである点に注意してください。
  オブジェクトは，要求されていなくても存在しえます。

ドメインには今のところ2つのアクションがあり，どちらも `:durative-action` です。
瞬時に完了するのではなく，開始から終了までの時間の幅を持つアクションを表します。
以降で書くものはすべてこれを真似るので，`process` をよく読んでください。

```lisp
(:durative-action process
  :parameters (?t - target)
  :duration (= ?duration 2)
  :condition (and
    (at start (processor-free))
    (over all (imaged ?t))
  )
  :effect (and
    (at start (not (processor-free)))
    (at end (processor-free))
    (at end (processed ?t))
  )
)
```

PDDL 2.1 には3つの時間修飾子が登場し，それぞれが条件を判定する，あるいは効果を適用する *タイミング* を示します。

- `at start` — アクションが開始する瞬間。
- `at end` — アクションが終了する瞬間。
- `over all` — 開始から終了までの区間全体。
  - この区間のあいだ，条件は途切れずに成り立っていなければなりません。

したがって `process` は，開始する瞬間にプロセッサが空いていることを判定し，実行中はずっと生画像が存在することを要求し，終了時にプロダクトが完成したことを記録します。
`(processor-free)` に対する2つの効果には，ここで名前を与えておく価値があります。
アクションは開始時にプロセッサを **確保し**，終了時に **解放します**。
PDDL 2.1 では，物理的に1つしかない機器をこのようにモデル化します。

では，プランナーを実行します。

```bash
uv run scripts/solve.py
```

```text
plan (2 actions):
0.000: observe(target-a) [5.000]
5.000: process(target-a) [2.000]
```

各行は `start: action(arguments) [duration]` と読み，時刻はモデルの抽象的な時間単位です。

> [!NOTE]
> もう一度実行すると，違うプランが返ってくることがあります。
> ここで探索を行っているエンジン Aries は，最短のプランではなく最初に見つけたプランを返し，実行のたびに同じ結果になるとは限らないからです。
> 時刻が掲載したものとずれることもあれば，2つのターゲットが逆の順序で扱われることも，重なって実行できるはずのアクションが直列に並ぶこともあります。
> このあとの要点はいずれも，モデルが何を許し何を禁じているかに基づくもので，たまたま得られた個々のプランには左右されません。

これがプランナーの仕事です。
処理の前に観測せよとは誰も指示しておらず，時刻 5 で処理を開始せよとも誰も指示していません。
プランナーは初期状態とゴールを与えられ，モデルが要求するタイミングですべての条件が成り立ち，最後にゴールが成り立つような，アクションの集合 *と開始時刻* を探索したのです。
`process` がこれより早く開始できなかったのは，`(imaged target-a)` を必要とし，それは `observe` が終了して初めて成立するからです。
この順序は指示によるものではなく，条件から導かれた結果です。

**ポイント:** ドメインは可能性を記述し，問題は1つの要求を記述し，プランナーはその両方を満たすアクションとタイミングを探索します。

## ステップ1: 持続アクションを完成させる

衛星は撮像と処理はできますが，まだ何も地上には届きません。
3つ目のアクションを取り込みます。

```bash
git restore --source=step-1 -- models/pddl/
```

これにより `(downlinked ?t)` と `(transmitter-free)` の述語が追加され，初期状態で送信機が空きになり，
ゴールが `(downlinked target-a)` に変わり，未完成の `downlink` アクションが追記されます。

このステップでは [`models/pddl/domain.pddl`](../models/pddl/domain.pddl) だけを編集します。
あなたが埋める箇所にはすべて `TODO` で印が付けてあり，全部で3つあります。

```bash
grep -n TODO models/pddl/domain.pddl
```

継続時間，条件，効果を自分で書きます。
コメントには，そのアクションが現実には何をしなければならないかが書かれており，必要な書き方はすべて `process` に示されています。
3つの `TODO` が求めているのは，日本語で書けば次のとおりです。

- 継続時間: 1回の送信にかかる時間は 3（README のいう抽象的な時間単位）。
- 条件: 2つ。送信の開始時に送信機が空いていること，および送信の全体を通じて `?t` のプロダクトが存在すること。
- 効果: 3つ。開始時に送信機を確保する，終了時に解放する，終了時に `?t` のプロダクトが地上に届いたことを記録する。

プレースホルダは正しい PDDL ではないため，置き換えるまでモデルは構文解析に通りません。
したがって，パーサがそのまま作業リストになります。

```bash
uv run scripts/solve.py
```

```text
could not read the model: Found invalid expression: todo-duration. From line: 51, col 28 to line: 51, col 41
```

エラーは行と列とともに，一度に1つずつ報告されます。
その箇所を埋めて実行し直すと，次の箇所が表示されます。

`target-a` を撮像し，処理し，ダウンリンクする3アクションのプランをプランナーが返せば，このステップは終わりです。

```text
plan (3 actions):
0.000: observe(target-a) [5.000]
5.000: process(target-a) [2.000]
7.000: downlink(target-a) [3.000]
```

エラーが出ないことだけでなく，プランそのものを確認してください。
`0.000` でダウンリンクする1アクションのプランは，構文解析には通っていてもモデルとしては失敗です。
条件がプロダクトの存在を要求していないため，プランナーは衛星がまだ取得していないデータを送信しているのです。

**ポイント:** 持続アクションとは，継続時間と，どのタイミングで判定するかを指定した条件の集合と，どのタイミングで適用するかを指定した効果の集合です。
アクション間の順序関係はどこにも記述されておらず，あるアクションが別のアクションの生成物を必要とすることから生じます。

## ステップ2: 実行できないプラン

これが重要なステップです。

運用側は，同じパス（衛星が地上局の上空を1回通過する間）で両方のターゲットを完了させることを求めています。
拡張されたゴールを取り込みます。

```bash
git restore --source=step-2 -- models/pddl/problem.pddl
```

ステップ1が未完成の場合や，このあとの実行でプランナーがタイムアウトする場合は，
代わりに `git restore --source=step-2 -- models/pddl/` でディレクトリ全体を取り込んでください。
送信機を確保したまま終了時に解放しない `downlink` は，送信が1回で済むステップ1では通ってしまい，2回目が続かなければならない今になって初めて解けなくなります。

2つの観測が同じ瞬間に始まらないプランが返ってきた場合は，取り込み直すのではなく，もう一度実行してください。
Aries は，モデル上は重なってもよいアクションを直列化して返すことがあり，取り込み直しても同じドメインが返ってくるだけです。
このステップで重要なのは，モデルがその重なりを *禁じていない* ことであり，特定の実行で実際に重なることではありません。

変わったのはゴールだけです。
ドメインは編集したままの状態であり，衛星の物理的な制約は何も変わっていません。
変わったのは要求だけです。
実行します。

```bash
uv run scripts/solve.py
```

```text
plan (6 actions):
0.000: observe(target-a) [5.000]
0.000: observe(target-b) [5.000]
5.000: process(target-a) [2.000]
7.100: process(target-b) [2.000]
9.100: downlink(target-a) [3.000]
12.200: downlink(target-b) [3.000]
```

最初の2行を見てください。
衛星のカメラは1台ですが，このプランはそのカメラで2つの異なるターゲットを同じ瞬間に撮像しています。
このプランは実行できません。

何かを変更する前に，この形のプランをモデルに照らして検査します。

```bash
uv run scripts/validate.py
```

このスクリプトは検査の前にモデルを解き直すため，表示されるプランは直前に読んだものとは限りません。
ここで重要なのは判定であり，その行は次のようになります。

```text
result:    VALID
```

バリデータはプランナーと一致しています。
どちらも正しく，このプランは確かにモデルを満たしています。
したがって，間違っているのはモデルの側です。

では，その理由を突き止めます。
必要な手がかりは，いま読んだプランの中にすでにあります。
2つの `process` アクションが現れますが，これらは重なって **いません**。
2つ目は1つ目の終了を待っています。
2つの `downlink` アクションも現れますが，これらも重なっていません。
2つのアクションの重なりを防げていない機器は，カメラだけです。

モデルを直してから，プランナーを再度実行してください。
2つの観測が分離されれば，このステップは終わりです。

そのとき，2つ目の観測は1つ目が終わった瞬間ちょうどではなく，わずかに後ろにずれて始まるはずです。
これは丸めによるものではありません。
PDDL 2.1 は，互いに干渉する2つの事象が同じ瞬間に起こることを禁じており，一方のアクションがカメラを解放し，他方が `(camera-free)` を判定するのはまさにその組み合わせなので，両者は分離されなければなりません。

もう1点，修正後のモデルも並行実行は許したままです。
異なる機器を使うアクションどうしは重なって構わないので，`observe` の実行中に `process` や `downlink` が走るプランも正当です。
Aries は最初に見つけたスケジュールで探索を止めるため，あなたの実行ではすべてが直列化されるかもしれませんが，モデルの中にそれらの重なりを禁じるものはありません。
並行実行そのものは，はじめから不具合ではありませんでした。
修正後のモデルは，実行不可能だった重なりだけを禁じ，それ以外は許しています。

**ポイント:** プランナーは間違っていません。
モデルが不完全だったのです。
条件はアクションが実行できるタイミングを制約するだけであり，状態を変えるのは効果だけです。
初期状態から真であり，かつ何ものもそれを偽にしない事実を要求しても，何も排除されません。
プランナーは与えられたモデルを探索し，モデルに抜けがあればそれをすべて利用します。

## ステップ3: スケジューリングだけではないプランニング

ここまで，どのプランのどのアクションも一意に決まっていました。
`(downlinked ?t)` を真にする方法は1つしかなかったため，プランナーが実際に決めていたのは順序とタイミングだけでした。
それはスケジューリングです。
プランナーに選択肢を与えます。

ステップ1とステップ2の冒頭の取り込みと違い，これは任意です。修正済みのモデルから始めたい場合だけ実行してください。

```bash
git restore --source=step-3 -- models/pddl/
```

高速ダウンリンクは主地上局が見えている間しか使えず，常に利用可能な低速のバックアップリンクがあります。
3つの変更を行います。1つ目は2つのファイルにまたがります。

1. ドメインに `(primary-visible)` 述語を追加し，問題の初期状態にも `(primary-visible)` を追加します。
2. パスの途中で地上局を見失うと送信が途切れるため，`downlink` の全体にわたって主地上局が見えていることを要求します。
3. `downlink-backup` アクションを追加します。
   条件と効果は `downlink` と同じですが，主地上局を必要とせず，継続時間は 3 ではなく 9 です（いずれも抽象的な時間単位）。
   どちらのリンクも1台の送信機を共有します。

`(primary-visible)` が何であり，何でないかに注意してください。
これは衛星が制御できない外部環境の事実なので，どのアクションも確保したり解放したりしません。
付くのは `over all` の条件だけで，効果は一切付きません。
これが `over all` の正しい使い方であり，`(camera-free)` はまさにそうではなかったのです。

プランナーを実行します。
ゴールを成り立たせるアクションが2つになったため，プランナーはどちらかを選ばなければなりません。
後述の理由により，どちらのリンクも正当です。

続いて，実験を行います。
[`models/pddl/problem.pddl`](../models/pddl/problem.pddl) の初期状態から `(primary-visible)` を削除し，もう一度実行します。
削除するだけで偽になります。`:init` に書かれていない事実は，未知ではなく偽だからです。
プランのダウンリンクの行は，バックアップリンクを指すようになります。

```text
...: downlink-backup(target-a) [9.000]
...: downlink-backup(target-b) [9.000]
```

何度か実行し，時刻ではなくアクション名を読んでください。
どの実行でも `downlink-backup` になります。そこが安定している部分です。
主地上局が見えない状況では，高速ダウンリンクは単に劣るのではなく使用不能であるため，プランナーはゴールを成り立たせられる唯一のアクションを選びます。

主地上局が見えている場合は1回の実行では判断できないので，そちらも何度か実行してください。
そのときはどちらのアクションも正当であり，モデルは高速ダウンリンクを優先するとは何も述べていないため，Aries はどちらを返すこともできます。
最初に見つけたプランで探索を止めるからです。
毎回同じ方が返ってくることも十分にありますが，それは探索がそこに落ち着いただけで，モデルが選んだわけではありません。
高速ダウンリンクを優先させたいのであれば，その優先度はモデルに書き込まなければならず，プランナーが当然に与えてくれるものではありません。
これはステップ2の要点を裏側から見たものです。
プランナーはモデルが述べたことをそのまま行い，それ以上のことはしません。

`(primary-visible)` を戻したうえで，自分の書いたものを模範解答と比べます。

```bash
git diff main -- models/pddl/
```

その差分はほとんどがコメントになるはずです。
`main` にはあなたが書く必要のなかった説明のコメントが入っており，あなたが解決した `TODO` のブロックもおそらくそのまま残っています。
読むべきなのはコメントではなく，条件と効果です。
そこが一致していれば，あなたのモデルは模範解答と同じことを述べており，差分がコメントだけになるのは想定どおりです。

**ポイント:** 時間プランナーは3つの異なることを決めており，ここまででそれぞれを個別に見てきました。

- **どの** アクションを使うか — `downlink` か `downlink-backup` か。
- **どの順序で** 行うか — 条件によって強制される `process` から `downlink` への順序，および共有する機器の確保によって強制されるターゲット間の直列化。
- **どの時刻に** 行うか — 継続時間，機器の確保，そして PDDL 2.1 が要求する分離と整合する開始時刻。

ここから先は，次の2つの方向が考えられます。

- 3つ目のターゲットを追加し，プランのどの部分がモデルによって直列化を強制されるのかを考える。
- 衛星に2台目のカメラを与え，プランナーがそれを使えるようにするにはモデルの何を変えなければならないかを考える。

## チェックポイント

各タグは，対応するステップの開始状態を保持しています。

| タグ | 状態 |
| --- | --- |
| `step-0` | `observe` と `process`，および単一ターゲットのゴール。 |
| `step-1` | 同じものに加えて，`TODO` マーカーが残された未完成の `downlink` アクション。 |
| `step-2` | 同じもので，`downlink` が完成し，ゴールが両方のターゲットに拡張されている。 |
| `step-3` | 同じもので，カメラが正しくモデル化されている。 |
| `main` | 同じものに加えて，高速ダウンリンクとバックアップリンクの選択がある。 |

つまり，あるステップの答えは，その次のステップのタグです。
ステップを飛ばしたいとき，あるいは作業ツリーをなかったことにしたいときは，該当するファイルを戻します。

```bash
git restore --source=step-2 -- models/pddl/    # ステップ1を飛ばす
git restore --source=step-3 -- models/pddl/    # ステップ2を飛ばす
git restore --source=main -- models/pddl/      # ステップ3を飛ばす
```

いつでも，自分の書いたものを模範解答と比べられます。

```bash
git diff main -- models/pddl/
```
