[English](README.md) | **日本語**

時間プランニング（temporal planning）のハンズオンチュートリアルです。

題材は，小型の地球観測衛星です。
衛星は，地上のターゲットを撮像し，各画像をオンボードでダウンリンク可能なプロダクトに変換し，各プロダクトを地上へ送信しなければなりません。
どの段階にも時間がかかり，衛星はカメラ，プロセッサ，送信機をそれぞれ1つずつ搭載しており，高速ダウンリンクで使う主地上局は可視の間しか利用できません。
これらのアクションのどれを，どの順序で，どの時刻に実行するかを決めるのが時間プランナーです。

このチュートリアルでは，あなたに実際に手を動かしてもらいます。
コードではなく，主にモデルを扱います。
PDDL 2.1 のモデルを読んで編集し，それに対してプランナーを実行し，返ってきたプランを読み，そのプランが衛星には決して実行できないものだと分かったらモデルを修正します。

時間プランナーは，モデルを満たすアクションとタイミングを探索します。
モデルに現実の制約が書かれていなければ，プランナーはその制約がないものとして探索します。

## 構成

- [`models/pddl/domain.pddl`](models/pddl/domain.pddl):
  PDDL 2.1 のドメイン。型，述語，持続アクションが書かれています。
- [`models/pddl/problem.pddl`](models/pddl/problem.pddl):
  PDDL 2.1 の問題。オブジェクト，初期状態，ゴールが書かれています。
- [`scripts/model.py`](scripts/model.py):
  モデルの特定と読み込み，および生成されたプランの整形。下の2つのスクリプトで共有されます。
- [`scripts/solve.py`](scripts/solve.py): Aries でモデルを解き，時間プランを表示します。
- [`scripts/validate.py`](scripts/validate.py): プランを，それが得られたモデルに対して検査します。
- [`docs/tutorial.ja.md`](docs/tutorial.ja.md): チュートリアル本体。最初のチェックポイントから模範解答までを扱います。

## 必要なもの

- Python 3.11 以降。
- [uv](https://docs.astral.sh/uv/)。
  - `uv sync` で依存関係が入ります。

## ツール

3つの要素が関わっており，それぞれ役割が異なります。

- **PDDL 2.1**: モデリング言語。
  あなたが書き，編集するのは，型，述語，持続アクション，そして解くべき問題です。
- **[Unified Planning](https://github.com/aiplan4eu/unified-planning)**: Python の統合レイヤー。
  PDDL をパースし，問題をエンジンに渡し，結果を返します。
  これは基盤であり，プランニング言語でもプランナーでもありません。
- **[Aries](https://github.com/plaans/aries)**: プランニングエンジン。
  制約ベースの時間プランナーであり，実際のプラン探索を担います。

あなたが書くのはモデルであり，読むのはプランです。
その間を埋めるのが，残りの2つです。

```text
PDDL 2.1 model
      |
      |  Unified Planning (engine: Aries)
      v
Temporal plan
```

## チュートリアル

チュートリアル本体は [`docs/tutorial.ja.md`](docs/tutorial.ja.md) にあります。
`main` には模範解答が入っているため，チュートリアルは `main` ではなくタグの付いたチェックポイントから始めます。

> [!CAUTION]
> これより下では模範解答を説明するため，ステップ2とステップ3の答えが分かってしまいます。
> チュートリアルを進めるなら，読むのはそれを終えてからにしてください。

## シナリオ

ドメインの名前は `orbiter` です。
型は `target` の1つだけで，問題ではその型のオブジェクトとして `target-a` と `target-b` の2つを宣言しています。

衛星は，カメラ，プロセッサ，送信機をちょうど1つずつ搭載しています。
それぞれが空いているかどうかを，`(camera-free)`，`(processor-free)`，`(transmitter-free)` という1つずつの述語で表しています。
モデルがそれらをどれだけ忠実に使うかが，このチュートリアルの主題です。

ミッションの進捗は，ターゲットごとに1つずつの事実 `(imaged ?t)`，`(processed ?t)`，`(downlinked ?t)` で記録されます。
ゴールは，両方のターゲットがダウンリンクされていることです。

1つの述語だけは，衛星ではなく環境を表します。
`(primary-visible)` は，高速ダウンリンクで使う主地上局が可視であることを意味します。
これは衛星と地上局の位置関係で決まるものであり，どのアクションもこれを確保したり解放したりしません。
この述語は，模範解答にのみ登場します。

模範解答には，4つの持続アクションがあります。

| アクション | 継続時間 | 意味 |
| --- | --- | --- |
| `observe ?t` | 5 | ターゲットを撮像する。カメラを確保する |
| `process ?t` | 2 | 生画像をプロダクトに変換する。プロセッサを確保する |
| `downlink ?t` | 3 | 高速ダウンリンク。実行中ずっと `(primary-visible)` を必要とする。送信機を確保する |
| `downlink-backup ?t` | 9 | 低速のダウンリンク。常に利用可能。送信機を確保する |

継続時間は秒ではなく，抽象的な時間単位で表されます。

## プランナーの実行

```bash
uv run scripts/solve.py
```

```text
plan (6 actions):
0.000: observe(target-a) [5.000]
5.100: observe(target-b) [5.000]
10.100: process(target-a) [2.000]
12.200: process(target-b) [2.000]
14.200: downlink(target-a) [3.000]
17.300: downlink(target-b) [3.000]
```

各行は `start: action(arguments) [duration]` という形式で，時刻はモデルの抽象的な時間単位です。

どちらのスクリプトも `--verbose` を受け取り，モデルのファイル名とエンジン名を示すヘッダを実行の先頭に表示します。
`validate.py` では，`VALID` という判定が何を意味し何を意味しないかの注記も追加されます。

Aries は充足を目指す（satisficing）プランナーです。
最短でも最速でもなく，最初に見つかったプランを返します。
このチュートリアルでは，最適化の指標も設定していません。

また，プランは実行ごとに変わります。
Aries は実行のたびに同じ結果を返すとは限らないため，正確な開始時刻や，2つのターゲットを扱う順序は異なりえます。
模範解答では，主地上局が可視の間はどちらのリンクも正当であり，モデルは両者の優先順位を定めていないため，選ばれるダウンリンクのアクションさえ上の例と異なりえます。
モデル上は重なってもよいアクションであっても，ある実行では直列化されることさえあります。
安定しているのはモデルが何を許し何を禁じているかであり，チュートリアルの学びはすべて，特定のスケジュールではなくそこに基づいています。
ここに記載したものと異なる出力が出るのは想定内です。

上のプランに見られる間隔は，干渉する2つの事象を分離するものです。
PDDL 2.1 では，あるアクションがリソースを解放する瞬間に別のアクションが同じリソースを確保することはできず，間隔の大きさはプランナーが決めます。
そのため `process(target-b)` は，`process(target-a)` がプロセッサを解放する 12.100 ではなく 12.200 に開始します。

どうやっても到達できないゴールを与えると，Aries はそのゴールが到達不能だと報告せず，停止させられるまで探索を続けます。
そのため `scripts/solve.py` は30秒のタイムアウトを渡します。
これほど小さなモデルでは，タイムアウトはほぼ常に，ある条件が決して満たされずゴールが到達不能であることを意味するので，スクリプトもそのように報告します。

## プランの検証

```bash
uv run scripts/validate.py
```

このスクリプトは現在のモデルを解き，得られたプランを，Unified Planning の `up_time_triggered_validator` エンジンを使って同じモデルに対して検査します。
エンジンは名前で選択されるため，他にどのエンジンがインストールされているかによって結果が変わることはありません。

混同しやすい2つの問いがあり，ここで答えられるのはそのうち1つだけです。

- プランは形式モデルを満たしているか。
  これはバリデータが検査することであり，バリデータに検査できるのはこれだけです。
- モデルは意図した現実の制約を正しく表現しているか。
  これは工学的な判断であり，どのバリデータにも下せません。

モデルが書き忘れた制約を突くプランは `VALID` と報告されます。
このチュートリアルでは，まさにそれを意図的に利用します。

## モデルの挙動

各ターゲットは，`observe`，`process`，そしてダウンリンクという3段階のパイプラインを通ります。
各段階は，ミッションの事実を通じて連結されています。
`observe` は `(imaged ?t)` を生成し，`process` はそれを必要とします。
`process` は `(processed ?t)` を生成し，どちらのダウンリンクアクションもそれを必要とします。
ダウンリンクは `(downlinked ?t)` を生成し，ゴールはそれを必要とします。
したがって，ある段階が，それに入力を与える段階より先に実行されることはありません。

模範解答では，どの機器もアクションの開始時に確保され，終了時に解放されます。
アクションは開始時にその機器が空いていることを表す述語を削除し，終了時に戻すため，同じ機器を必要とする2つのアクションが時間的に重なることはありません。
異なる機器を必要とするアクションにはそのような制約がなく，自由に並行実行できます。
そのため，カメラがすでに次のターゲットを撮像している間に，あるターゲットを処理することもモデル上は許されていますが，充足を目指すプランナーが常にその選択をするとは限りません。

`(primary-visible)` は種類が異なります。
これは，アクションが確保するリソースではなく，環境が制御する条件です。
そのため `downlink` では，`(primary-visible)` を，対応する効果を持たない `over all` 条件として書いています。
このアクションは継続時間の全体にわたって主地上局が可視であることを要求しますが，それを実現するためには何もしません。
`downlink-backup` は主地上局をまったく必要とせず，継続時間は3倍です。
したがって，2つのリンクは優先順位ではなくトレードオフの関係にあります。
